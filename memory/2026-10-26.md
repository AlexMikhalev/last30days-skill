## Lessons Learned

1. **A stored baseline is not a baseline on a shared host.** Comparing
   a baseline captured at one moment against a candidate captured at
   another measured the HOST, not the code — producing a false `PASS`
   on a 38% "improvement" and a false `REGRESSION` on unchanged code.
   Interleave the pair and compare the *pair*.

2. **Prove the perturbation actually landed before trusting a verdict.**
   A sabotage helper doing `range(os.environ.get(...))` raised
   `TypeError`; two mutation arms never ran and were reported as
   passing. And a harness whose baseline was captured with different
   `--samples`/`--iterations` made every arm `INCOMPARABLE` — so the
   arms proved nothing while appearing to run.

3. **Measure the perturbation, do not assume its magnitude.** A
   `time.sleep(0.000003)` imposed far more than 3 µs; a fixed spin count
   changed the measured file's digest and so produced `INCOMPARABLE`
   instead of `REGRESSION`. Put the magnitude in an environment input so
   the measured bytes stay stable, and calibrate by measurement.

4. **Check what is competing for CPU before blaming the code.** An 88%
   metric variance was my own load-bearing harness running concurrently.
   CPU time == wall time (CPU-bound, not preempted), and disabling GC
   made it *worse*. I wrongly blamed GC, then scheduler jitter.

5. **Ask the forge, not the filesystem.** `find` over `/home/alex` found
   no fork repositories, and I concluded they were absent. Both are on
   Gitea. A private-repository 404 is not proof of absence either.

6. **An unauthorised API call cannot produce a version number.** I
   claimed the earlier wrong figures were "artifacts of the unauthorised
   probe" — impossible, since that path returns no version at all. The
   origin was unknown; withdrawn rather than re-explained.

7. **Count before calling something a defect.** "Zero-asset releases are
   a packaging defect" was refuted by counting: skills 0/3, grok-build
   0/10, proxy 8/27. The zero-asset shape is the norm for
   source-consumed products. The real question was the probe's policy.

8. **A gate that cannot decide must not pass.** `INDETERMINATE` exiting
   0 meant the effective threshold was ~19.5% (later ~29–51%), not the
   required 10%. Fail closed.

9. **Substitute corrections into the body; do not append them.** The
   second reviewer rejected the revision because "fixes were added, not
   substituted" — the old false claims were still there, contradicting
   the corrections.

10. **Rebind credentials that were exposed during diagnosis.** The
    Gitea database password and runner token surfaced in output. Both
    need rotating. Values are redacted in all notes.

## Regressions
- [2026-10-26] Performance gate compared a stored baseline against a later candidate, measuring the HOST instead of the code → false verdicts in both directions. Rule: measure baseline and candidate PAIRED in the same time window and compare the pair.
- [2026-10-26] Sabotage helper raised `TypeError` from `range(os.environ.get(...))`, so two mutation arms never ran but were reported as passing. Rule: every mutation arm must prove it applied its perturbation before its verdict counts.
- [2026-10-26] Harness baseline captured with different `--samples`/`--iterations` than the arms made every arm `INCOMPARABLE`. Rule: the harness captures its own baseline with its own parameters.
- [2026-10-26] Overhead instrument timed one probe call instead of the whole step; the figure did not reproduce (0.67% vs 0.000%). Rule: an overhead claim must time the thing it claims to measure, and be re-measured after the fix.
- [2026-10-26] My own harness, running concurrently with the measurement, inflated observed variance to 88% and I blamed GC, then scheduler jitter. Rule: establish that nothing of mine is competing for CPU before diagnosing a shared host.
